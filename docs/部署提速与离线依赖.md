# 部署提速与离线依赖

本次实现两项优化：在 GitHub Actions（自动化工作流）之间保存镜像构建缓存，以及提前生成 Linux 宿主机工具的离线依赖包。代码和工作流提交到 `main` 后才在 GitHub 生效；本地验证不代表已经完成云端发布。

## 1. 应用镜像构建缓存

原路径继续使用：GitHub 构建应用镜像 → 推送 ACR（阿里云容器镜像服务）→ 服务器拉取镜像。Python / Node 依赖在 GitHub runner（执行机）构建镜像时下载，服务器运行应用时无需重新安装这些依赖。

`ci.yml` 和 `publish-acr.yml` 现在通过 Docker Buildx（镜像构建工具）导入、导出 GHA 缓存，使用两个独立 scope（缓存范围）：

| 镜像 | scope | 失效条件 |
|---|---|---|
| backend | `ai-notes-backend-linux-amd64` | 基础镜像、`requirements.lock` 或之前的构建步骤改变 |
| frontend | `ai-notes-frontend-linux-amd64` | 基础镜像、`package.json`、`package-lock.json` 或之前的构建步骤改变 |

两个 scope 均使用缓存服务 `version=2`、`mode=max`，包含中间构建层。只改源码时，预期复用 `pip install` / `npm ci` 所在依赖层，继续执行后续源码构建。基础镜像标签指向新内容、依赖锁变化或缓存被清理时仍需下载依赖。首次构建不会凭空提速。

- `main` 的 push / 手动工作流可以保存缓存；PR（拉取请求）和其他分支仅恢复缓存。
- 发布仍先运行完整 CI，保留迁移、后端测试、前端类型 / 构建 / 测试、OpenAPI、Compose 和隔离 HTTPS 检查。
- CI 加载一次前后端验证镜像，复用于隔离 HTTPS 检查，移除重复构建。发布镜像依然带唯一 release tag、提交标识，并记录推送后的 digest（镜像内容摘要）。
- 继续通过 GitHub Secrets 提供 ACR 登录信息；不需要新增 ACR 缓存仓库、云资源或服务器权限。

查看效果：打开 GitHub → Actions → `Project checks` 或 `Publish development images to ACR`，展开两个镜像构建步骤，查找 `importing cache`、依赖步骤的 `CACHED` 和最后的缓存导出结果。缓存命中率、测试与镜像上传耗时共同决定总时长；不能承诺固定的提速倍数。

恢复旧行为：撤回两个工作流中的缓存 / Buildx 改动并正常提交。缓存不会改变应用数据或数据库；缓存过期只会恢复冷构建。无需清理服务器镜像或数据卷。

## 2. 宿主机工具离线包

监测和备份工具运行在宿主机，和应用容器的依赖分开。新流程先在匹配的 Linux 环境下载 wheel（Python 二进制安装包），再把已验证的包带到服务器，在新虚拟环境中断网安装。

| profile（用途） | 来源与内容 |
|---|---|
| `monitoring` | `backend/requirements.lock` 中的 SQLAlchemy、psycopg、psycopg-binary、typing-extensions |
| `backup` | 同一锁文件中适用于 Linux 的完整后端依赖，供备份 / 恢复工具使用 |

两种包都包含固定 `pip==24.0` 引导依赖。目标为 Linux / x86_64、CPython 3.12、glibc ≥ 2.36；构建基线为 `python:3.12-slim-bookworm`。当前 Ubuntu 24.04 服务器符合该目标。不能使用 Windows 虚拟环境代替，也不能装到其他 Python 小版本或 ARM / Alpine 环境。

包包含 `install.py`、源锁文件、用途锁文件、带 SHA-256 的安装清单、`manifest.json` 和 `wheels/`。校验会拒绝缺失、额外、被修改或带软链接的内容，也检查包名、版本、平台和 wheel 元数据。SHA-256 用于完整性核对；取得包时仍需信任原始提交及对应工作流制品的来源。

### 在 GitHub 生成

提交工作流到 `main` 后，在仓库 Actions 中找到 **Build offline operations wheelhouses** → **Run workflow**，选择 `main`。它会同时生成两种用途，并依次完成：

1. 在 Linux 构建容器内下载固定版本的 wheel，使用独立用途缓存。
2. 校验导出的全部文件。
3. 在 `--network none` 的干净容器中创建虚拟环境，安装、运行 `pip check` 和导入检查。
4. 只有检查通过才上传 Artifact（构建制品），名称含用途、平台和 Git 提交，保存 14 天。

该工作流无 ACR 凭据，不登录服务器，也不安装生产环境。依赖锁或安装脚本变化后重新生成，使用对应提交的完整制品。

### Windows 本机生成与校验

执行位置：项目根目录，PowerShell 7；Docker Desktop 需要运行 Linux 容器。命令只生成本地包，不触碰业务数据库。

```powershell
$bundlePath = Join-Path $PWD '.local\artifacts\ops-wheelhouse-monitoring'
docker buildx build --platform linux/amd64 `
  --file ops/wheelhouse/Dockerfile --target artifact `
  --build-arg PROFILE=monitoring `
  --output "type=local,dest=$bundlePath" .
if ($LASTEXITCODE -ne 0) { throw 'wheelhouse build failed' }

& backend/.venv/Scripts/python.exe scripts/ops_wheelhouse.py verify --bundle $bundlePath
if ($LASTEXITCODE -ne 0) { throw 'wheelhouse verification failed' }
```

首次使用请选择尚未存在的输出目录。生成备份用途时，将 profile 和输出目录名中的 `monitoring` 同时改为 `backup`。构建使用 Dockerfile 专用的上下文白名单，只发送脚本及锁文件，不发送 `.env`、`.local`、备份、私钥或 `AGENTS.md`。

预期校验输出类似 `{"ok": true, "profile": "monitoring", "files": 11}`。实际文件数随锁文件与用途变化，以当前包输出为准。Windows 支持校验；安装必须在匹配的 Linux 中进行。

若要独立复验断网安装，先在线准备基础镜像，再运行隔离容器：

```powershell
docker pull --platform linux/amd64 python:3.12-slim-bookworm
if ($LASTEXITCODE -ne 0) { throw 'test base pull failed' }
docker run --rm --platform linux/amd64 --network none --read-only --cap-drop ALL `
  --security-opt no-new-privileges --tmpfs /tmp:rw,exec `
  --mount "type=bind,source=$bundlePath,target=/bundle,readonly" `
  python:3.12-slim-bookworm `
  python /bundle/install.py install --bundle /bundle --venv /tmp/ops-test
if ($LASTEXITCODE -ne 0) { throw 'offline installation failed' }
```

预期包含 `No broken requirements found.` 以及最终 `"ok": true`。容器只挂载离线包，临时环境随容器退出移除。

### 后续服务器使用边界

此次没有上传包、替换当前 `.ops-venv`、修改定时器或重启服务。将来更新服务器工具时，先按本地运维记录核对连接方式、维护授权、当前解释器及回退环境，再传完整包并验证。

服务器安装命令模板（路径均为示例，需要换成当次明确选择的绝对路径）：

```bash
python3.12 /path/to/trusted-bundle/install.py verify --bundle /path/to/trusted-bundle
python3.12 /path/to/trusted-bundle/install.py install \
  --bundle /path/to/trusted-bundle --venv /path/to/new-ops-venv
```

目标父目录需已存在，目标虚拟环境必须是新路径。脚本用 `venv --copies --without-pip` 创建独立环境，再通过包内 pip 引导；安装使用 `--no-index`、包内 wheel 和哈希清单，并屏蔽继承的 pip / Python 配置。不依赖服务器 `ensurepip`，不安装系统包。

校验失败会直接退出；安装中途失败会保留新建目录供排查，不能将失败目录当成已完成环境再次使用。改用另一个新路径重试。切换服务解释器前，必须完成工具自检及当次批准的验证；旧环境保持可用，切换异常时恢复原解释器路径。不要删除旧环境或复用旧路径进行覆盖安装。
