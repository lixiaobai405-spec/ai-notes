# 文件引用保留与安全清理

本轮提供独立手工运维工具，**尚未对开发或公网数据执行清理，未启用自动任务**。默认命令只生成预演。设计见 [确认方案](superpowers/specs/2026-10-25-file-gc-design.md)，验证范围见 [阶段记录](task-evidence/2026-10-25-file-gc.md)。

## 保留策略

所有已登记 `File.object_key` 和 `FileVariant.object_key` 均保留，包括无当前页面、回收站、expired、rejected、可重试失败和历史内容；不按“页面已不显示”判断文件可删。当前页、历史页面、PDF 原件/导入/上传/任务、AI 冻结对象、保存来源及文字原版本一并核验。旧 AI reading 键即使不同于当前变体，仍是保留根。损坏引用或不明来源使操作失败，不把解析失败当作没有引用。

本轮不删除任何数据库行、不裁剪回收站或历史版本、不回收已登记业务文件。它解决的是 Worker 强杀、上传/存储失败等留下的**未登记且无引用的对象残片**；PDF PUT 已对齐先登记临时键再发送，响应丢失时也能进入既有清理路径。

预演完整枚举配置 local 根或 OSS prefix 的当前可见对象。候选必须满足全部条件：无引用、严格匹配应用键、最后修改时间严格早于预演时刻减 7 天（可增加，不能减少）、单件不超过 128 MiB。严格允许的键为：

```text
<owner-uuid>/<file-uuid>/original
<owner-uuid>/<file-uuid>/<worker-uuid>-original.jpg
<owner-uuid>/<file-uuid>/<worker-uuid>-reading.jpg
<owner-uuid>/<file-uuid>/<worker-uuid>-thumbnail.jpg
restore_<32hex>/<file32hex>/original
restore_<32hex>/<file32hex>/v_<variant32hex>
```

UUID/hex 为小写；未知名字只计数保留，不尝试删除。local 引用对大小写及组件尾点/空格做保守保留匹配，避免 Windows 同一物理路径的不同拼写导致误删；在大小写敏感文件系统上可能多保留。OSS 保持精确大小写语义。符号链接、junction/reparse、硬链接和非普通文件均拒绝扫描或操作。

## 配置与权限

工具从仓库根运行，使用已安装后端依赖的隔离环境。Ubuntu 可沿用 [定时备份文档](定时备份与失败通知.md) 的独立 `.ops-venv`；Windows 使用 `backend/.venv/Scripts/python.exe`。没有新依赖、数据库迁移或 API。

配置只包含路径、Bucket/prefix 和**环境变量名**，不接受命令行明文密码或 Key。示例 [ops/file-gc.example.json](../ops/file-gc.example.json) 必须复制到私密目录后修改，不能直接从宽权限仓库目录读取作为配置。状态根与 local 源目录必须相互独立，所有路径使用绝对路径。

Ubuntu 准备示例（位置 `/opt/ai-notes`，只创建配置，不清理）：

```bash
umask 077
mkdir -p .local/file-gc /var/lib/ai-notes/file-gc-state
chmod 700 .local/file-gc /var/lib/ai-notes/file-gc-state
cp -n ops/file-gc.example.json .local/file-gc/config.json
chmod 600 .local/file-gc/config.json
```

通过本机私密环境提供 `FILE_GC_DATABASE_URL` 和独立运维 OSS 变量。数据库连接必须指向本次存储对应的实例；不能把别的库的引用图用在当前 Bucket 上。沿用备份连接文件时，可在未开启 shell tracing 的私密终端中载入，不输出其内容：

```bash
export FILE_GC_DATABASE_URL="$(cat .local/backup-database-url.txt)"
```

该文件的准备、数据库回环端口及首次端口变更维护要求见 [定时备份准备](定时备份与失败通知.md#启用前准备ubuntu-宿主机未在本轮执行)。GC 不替你开启数据库端口或修改服务器配置。

local 配置的 storage 替换为：

```json
{"backend": "local", "root": "/absolute/private/live-files"}
```

状态目录在 POSIX 要求当前所有者、目录 0700 / 文件 0600；Windows 检查所有者与 DACL，仅允许当前用户、SYSTEM、Administrators/Owner Rights。Python 3.13+ 的私密目录创建已实测，较早 Windows 若目录继承宽权限会安全拒绝，需要事先由管理员正确配置 ACL，不绕过校验。

OSS 预演需要限定 prefix 的当前对象枚举、HEAD/GET；执行还需查询 Bucket 版本状态、删除当前对象，恢复需枚举该键版本并删除本工具创建的**删除标记版本**。使用独立运维身份，按用途授予权限，不扩大应用 API 的权限。工具不枚举或永久清理数据历史版本。

## 预演与审阅

Ubuntu 仓库根执行（用途：只读引用和存储清单；预期：`status=planned`、plan 文件名、digest 和统计）：

```bash
.ops-venv/bin/python -m scripts.file_gc --config .local/file-gc/config.json plan
```

省略子命令也仅执行 plan；可用 `plan --grace-days 14` 延长宽限。终端不输出对象键、正文、数据库地址或凭据。完整候选身份位于状态根中的私密 `plan-<id>.json`，需在本机审阅 `objects`，确认它们确属本应用残片，再使用本次返回的摘要。摘要只是绑定本次审阅内容，不是防同机管理员篡改的签名。

清单最多 50000 个对象，候选总和最多 512 MiB，计划最多 24 小时有效；超限需停止并另行规划，不截断清单后执行。执行器默认有 600 秒预算，扫描、分页和分块复制均检查预算；OSS 单次请求仍受 5 秒连接/20 秒读写限制，不承诺内核或存储失去响应时的硬实时截止。

## 维护窗口、执行与核验

1. 先按现有整站工具完成并校验备份。整站备份只收集引用对象，不能替代 GC 自己的孤儿对象归档。
2. 停止备份 timer / 手工备份、导出、恢复、部署和其他维护操作，确保它们不与 GC 并行。当前 GC 没有自动接入 timer，也不会使用 T14 状态锁假装跨工具互斥。
3. 在原 Compose 文件/环境组合下记录 API/Worker 原先运行状态，先让任务结束或主动取消，再停止 API、所有 Worker、迁移及其他数据库/OSS 写入者。也要停止直接 SDK 脚本和对象生命周期删除。工具不自动停服务，不把两个确认参数当作实际检测。
4. 核对没有在途上传、queued/running/残余租约任务、AI 运行或活动 PDF 导入。pending/received 上传即使时间过期也保守阻止执行，需让现有维护先将其标 expired。已经 expired 的 PDF 上传原件仍保留，可恢复重试；重新激活后再次阻止 GC。
5. 在停写后重新生成 plan 并审阅，避免在线预演期间的变化。执行还会取得独立状态锁、数据库全局 advisory lock（建议锁）及引用表 SHARE 锁，重新读取完整引用、活动状态、后端身份和每个候选身份；变化即拒绝。数据库锁不能停止已经发出的对象 PUT，因此完整停写仍是前置条件。

Ubuntu 仓库根，使用真实审阅的文件名/摘要替换占位符（用途：先归档再移出在用存储）：

```bash
.ops-venv/bin/python -m scripts.file_gc --config .local/file-gc/config.json apply \
  --plan plan-REVIEWED_ID.json --digest REVIEWED_PLAN_SHA256 \
  --maintenance-confirmed --writers-stopped
```

工具先把**全部候选**复制到状态根的 `run-<id>/objects/`，逐件核对大小/SHA-256 并持久化清单，确认材料完整后才开始删除。POSIX 同步文件与新增文件名所在目录，失败不进入删除。逐件先写删除意图，再操作，再保存回执；任何失败/未知结果停止后续删除，不盲目重试。

正常返回 `complete`、bundle 名和 digest。`stopped` / `unknown` 表示部分执行或响应未知，退出码 1；保留原状态及归档，先用 status 核验，不能重新 apply 原计划冒充幂等执行：

```bash
.ops-venv/bin/python -m scripts.file_gc --config .local/file-gc/config.json status --bundle run-RESULT_ID
```

仅恢复原先运行的服务，不启动原先停止的服务；按既有部署文档验证 API、Worker、原页/来源及备份，再离开维护窗口。归档没有自动过期删除，本轮不会替你清除恢复材料。

## 恢复与故障处理

保持维护停写状态，审阅 status 返回的 bundle 摘要后执行：

```bash
.ops-venv/bin/python -m scripts.file_gc --config .local/file-gc/config.json restore \
  --bundle run-RESULT_ID --digest REVIEWED_BUNDLE_SHA256 \
  --maintenance-confirmed --writers-stopped
```

恢复先校验精确目录布局、私密权限、manifest 与全部 payload 哈希，拒绝额外/缺失文件、路径逃逸、别名或损坏。local 只补缺失键，已有内容同哈希返回 `already_present`，不同内容返回冲突；通过 Windows 不覆盖 rename / Linux `renameat2(RENAME_NOREPLACE)` 原子发布，不留双硬链接崩溃窗口。其他 OS/文件系统若不支持则安全拒绝，不降级到覆盖或硬链接。发布后强杀的恢复重试已隔离实测。

OSS 只允许版本控制 `Enabled` 执行。无版本或 `Suspended` 可预演，apply/restore 拒绝。当前 SDK 无 If-Match 删除，且版本桶忽略 PUT 的 forbid_overwrite，工具不以 HEAD→PUT 假装原子防覆盖。删除不带 versionId，记录本工具新建的删除标记；恢复核验原数据版本/hash、完整版本分页和确属本次的最新标记后，**只删除该标记 versionId**，不删除数据版本、不 PUT 覆盖并发新版本。若删除回执未知、原版本缺失或版本发生变化，保留归档并返回人工核验/冲突，不猜测标记。

OSS delete marker 使当前对象不可见，但旧数据版本仍计费；隔离归档也占空间。因此结果里的 deleted 是移出当前在用视图，不代表账单或磁盘净容量已经减少。[OSS DeleteObject](https://www.alibabacloud.com/help/en/oss/developer-reference/deleteobject)、[版本枚举](https://www.alibabacloud.com/help/en/oss/developer-reference/listobjectversions)。

Windows 已验证文件 flush、权限和进程崩溃后的逻辑恢复，但标准库没有等同 POSIX 的可移植目录断电保证；正式维护执行以 Ubuntu 为目标。本机测试、Linux 容器和调用顺序验证均不等于真实断电演练、真实 OSS 或公网验收。
