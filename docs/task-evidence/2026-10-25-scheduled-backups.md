## 实现

- `scripts/site_backup_schedule.py`：私密路径配置、维护时间检查、Compose 项目/容器身份核验、迁移运行拒绝、停止原运行服务、既有 backup/verify CLI、独立尽力恢复、状态查询与通知重试。
- `scripts/site_backup_state.py`：原子受限 JSON、跨平台稳定 OS 锁、私密成功回执、只读保留计划及固定文件集合清理。仅管理登记目录，保留最近 N 份当前可完整验证的副本，未知/损坏/旧 schema/路径别名/硬链接均保留。
- `scripts/site_backup_process.py`：POSIX 子进程输出/时间上限及进程组清理，组长退出后仍清理后代；实际执行入口对 Windows 在创建进程前明确拒绝。
- `ops/backup-schedule.example.json`、systemd service/timer、单独 `compose.backup.yaml` 与 [运维说明](../定时备份与失败通知.md)。数据库覆盖仅绑定 `127.0.0.1:55435`，没有应用到业务环境。
- 不新增依赖、业务 API、数据库迁移或产品界面。失败先写本地独立事件，可选通知程序接收脱敏 stdin JSON；默认无外发。通知程序退出成功不等于实际渠道终端送达。

## 故障证据与修复

- 状态/保留模块初始 RED 为模块不存在；其后围绕最新备份损坏、未知目录、超限、回执变化、别名/硬链接与 OS 锁补回归并 GREEN。
- 单独 Worker 启动失败曾阻断 API 恢复；新增回归先 RED，再按服务分别尝试恢复，最终报告失败并保留恢复现场。
- 通知状态落盘失败曾覆盖原备份错误；新增回归先 RED，再隔离状态/通知记录异常，保留原错误及尽力记录的次要错误码。
- 大量保留记录曾超过 64 KiB 状态限制；改为各类总数和前 20 项样本。
- 父进程退出、后代继续持有 stdout 时，原超时清理会提前返回；回归先复现约 4.19 秒才退出，再使 POSIX 始终清理整个进程组。实际生产目标为 Ubuntu，Windows 不再提供真实外部命令执行承诺；四项实际进程测试在 Linux 全部通过。
- Worker 容器身份变化曾阻断身份未变的 API；新增回归先 RED，再跳过变化目标、恢复其余确认目标，保留恢复记录并返回身份变化错误。
