# 登录会话的请求验证恢复

用户在 PDF 导入时报告 `请求验证失败，请刷新页面`，请求标识为 `b37aabbc-e136-4eb3-901b-4817dd73c712`。现有日志未保留该条 INFO 记录，因此不把该编号描述为已成功关联到某个具体上传阶段。依据对应 `csrf_invalid` 错误路径，在隔离 `notes_test` 稳定复现：保留有效登录 Cookie、只删除或覆盖 CSRF Cookie，读取账户仍成功，但创建笔记返回 403；修复前两项回归均失败。

## 原因与修复

登录时两个 Cookie 均有持久期限，但旧 `/auth/csrf` 不传 `max_age`，每次把 CSRF Cookie 改写为浏览器会话 Cookie。关闭浏览器后可能只丢失 CSRF Cookie。该接口还会直接回显旧 Cookie，缺失时生成新的随机值，没有同步当前会话保存的摘要；刷新无法恢复。

改为从高熵 HttpOnly 登录令牌通过带用途隔离的 HMAC 派生稳定 CSRF 值，新登录和注册直接使用该值，数据库仍仅保存摘要。已有有效会话在获取令牌时校准旧摘要，同一会话并发获取的结果相同。此接口只锁会话行，不反转既有账户撤销的锁顺序；Cookie 期限不超过会话剩余整数秒，不延长数据库登录期限。显式跨源 Origin 和 `Sec-Fetch-Site: cross-site` 被拒绝。

写请求的来源校验、常量时间摘要比对、失效会话拒绝和前端跨账号屏障保持生效。没有自动重放业务请求、创建额外登录、放宽验证或更改密码。匿名登录前的 Cookie / Header 双提交仍保留。旧随机会话首次校准时，已在途的旧令牌可能失效一次；刷新后重新发起操作即可。没有 API 契约、依赖或迁移变更。
