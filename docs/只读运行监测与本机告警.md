# 只读运行监测与本机告警

本工具属于 T15 最小运行监测，设计见 [已确认方案](superpowers/specs/2026-10-26-m1-monitoring-design.md)。交付内容为独立采集脚本、私密配置示例、本机快照与告警记录及 systemd 模板。**本文中的服务器准备、授权配置、安装与启用步骤均为后续操作说明，本轮没有执行公网部署、启用定时器、发送通知或调用真实模型。真实 PostgreSQL 与 Ubuntu 宿主机结果须按阶段证据和验收记录单独确认。**

## 运行位置与只读边界

从完整仓库根目录运行 `python -m scripts.site_monitor`，使用已有独立运维虚拟环境和项目锁文件。它不导入应用的真实配置，不提供公开接口，也不在 API / Worker 容器中运行。

采集器只执行 PostgreSQL 聚合查询和本机 Docker 的 `ps`、投影后的 `inspect`、`stats`；数据库事务使用 `REPEATABLE READ, READ ONLY`，结束后回滚并关闭连接。它不修改业务记录、不领取或重试任务、不重启容器、不执行迁移、不删除文件或对象。每次采集会写入工具自己的私密状态目录。

Docker 访问固定为本机 `/var/run/docker.sock`，按配置的精确 Compose 项目和服务筛选、复核容器身份；不读取容器环境变量、日志或完整 inspect 输出。不要为此给应用容器挂载 Docker socket。模板以 root 执行，部署时应单独审阅这一运维权限，不能把只读命令集合理解为 Docker socket 本身具有只读权限。

Ubuntu 宿主机是完整采集的目标环境。Windows 支持纯逻辑和隔离数据库验证，内存及 Docker 指标明确不可用；能读取的本机磁盘容量不代表 Ubuntu 实测。检测到容器命名空间，或无法确认宿主机来源时，内存与磁盘不作为宿主机指标报告。隔离 Linux 容器中的模拟 `/proc` 和 Docker 输出也不算真实 ECS 验收。

## 配置与私密路径

示例见 [`ops/monitoring.example.json`](../ops/monitoring.example.json)。实际配置另存，不直接把仓库中的示例当成生产配置。

| 项目 | 示例 / 规则 |
|---|---|
| 配置文件 | `/opt/ai-notes/.local/monitoring/config.json` |
| 私密环境文件 | `/opt/ai-notes/.local/monitoring/monitoring.env`，仅由维护者配置，不进入 Git |
| 数据库环境变量名 | `AI_NOTES_MONITOR_DATABASE_URL`；JSON 只保存变量名，不保存 URL 或密码 |
| 独立状态目录 | `/var/lib/ai-notes/monitoring`，不与 GC、备份状态或业务文件目录混用 |
| Compose 项目 | 示例为 `ai-notes-server`，须与现场实际项目名一致 |
| 服务 | 示例为 `db`、`api`、`worker`、`web`；一次性迁移容器不列作常驻服务 |
| 磁盘别名 | 示例 `system`、`data`、`backup`；值为现场真实绝对路径，不会输出原路径 |
| 统计窗口 | `window_minutes=60`，CLI 允许 1–1440 分钟 |
| 采集预算 | `sample_timeout_seconds=30`，允许 5–60 秒 |
| 快照过期 | `stale_after_seconds=180`，允许 60–3600 秒，必须大于采集预算 |

配置字段严格校验，未知字段、重复服务、无效路径、非有限数值阈值等会拒绝。内存、每个配置磁盘、数据库连接和 Job / AI 最老等待都必须有阈值。百分比严重阈值不能超过 100；同一指标的警告阈值不得大于严重阈值。

Linux 上配置目录和状态目录归运行用户所有，权限为 `0700`；配置、环境文件和状态文件为 `0600`。路径不能经过软链接或 junction。Windows 使用受限 ACL（访问控制列表），普通 `chmod` 不能替代这一检查。缺失或不符合权限的文件应由维护者确认原因，不要通过放宽检查继续运行。

状态中的目标标识包含配置和实际数据库连接身份的脱敏指纹；不保存明文连接 URL 或密码。更换被监测数据库或 Compose / 服务 / 磁盘目标时使用新的 `state_root`，保留原目录用于审阅，避免把旧目标告警当作新目标已恢复。修改阈值或统计窗口会使旧快照返回 `monitoring_policy_changed`，重新采集后才使用新策略。

指纹也保守纳入 `PGHOST`、`PGHOSTADDR`、`PGPORT`、`PGSERVICE` 等libpq路由环境默认值，避免同一URL因环境改变而指向别处；即使某个默认值被URL覆盖，改变它也要求核对目标并使用新状态目录。凭据默认值不进入指纹。服务文件内容、DNS或同名服务背后的物理集群更换无法由URL/环境指纹自动识别，运维更换时仍须另用状态目录。环境变量含义见[PostgreSQL 16官方说明](https://www.postgresql.org/docs/16/libpq-envars.html)。

## 数据口径

所有时间使用带时区的 UTC 时间。数据库窗口为 `[window_start, window_end]`，两端都包含；它是每次采集重新计算的滑动窗口，不能把相邻快照的窗口计数相加。

| 分组 / 字段 | 含义与限制 |
|---|---|
| `host.memory` | 读取 Linux `MemTotal` 和 `MemAvailable`；使用率为 `(total - available) / total` |
| `host.disks.<alias>` | 配置路径所在文件系统的总量与可用空间，使用率为 `(total - free) / total`；多个路径可能属于同一文件系统，不应重复相加 |
| `host.containers.services.<service>` | 容器数量、正常运行数量、CPU 和内存资源摘要；容器内存采用 Docker CLI 扣除缓存的口径，与宿主机内存分别解释；多实例标记 `ambiguous` |
| `database.connections` | 整个 PostgreSQL 集群的 `client backend` 数，包含采集器自己的连接；分母为配置的 `max_connections`，不代表普通角色扣除预留连接后的可用额度 |
| `database.jobs` | 当前可运行队列、未来调度队列、运行数、失败总数和过期租约；`oldest_ready_seconds` 从 `created_at` 与 `run_after` 中较晚者算起，只计算已到可运行时间的排队任务 |
| `database.jobs.failed_created_window` | 窗口内创建、当前为失败的 Job 数；现有表无可靠失败时间，不能称为窗口内发生的失败事件数 |
| `database.ai` | 当前排队 / 运行数、最老排队时间、过期租约；错误数按终态 `finished_at` 落在窗口内计算，包含 `failed`、`interrupted`、`truncated`，不把用户取消计作模型错误 |
| `database.ai.provider_errors_finished_window` | 上述错误中属于固定提供商错误码的子集，不输出原始错误文本 |
| `database.uploads.created_window` | 窗口内创建的 `UploadSession` 数，不计派生 PDF 页图文件；不是 HTTP 请求总数 |
| `expired_created_window` / `rejected_created_window` | 上述上传创建队列中，当前已过期的上传数 / 对应文件当前被拒绝数 |
| `processing_failed_created_window` | 窗口内创建、当前失败的 `image.process` / `pdf.import` Job 数，具有独立的任务创建队列口径 |
| `pdf_rejected_created_window` | 窗口内创建、当前为 `rejected` 的 `PdfImport` 数；PDF 内容拒绝可能对应成功结束的 Job，须与任务执行失败区分 |
| `database.usage` | `finished_at` 在窗口内的终态 `AiRun`，包含成功、失败、取消、中断及截断；只取已经聚合的 `AiRun.usage`，不再次累加 `AiStep` |
| `known_total_tokens` | 合法、已知的 `total_tokens` 总和；有运行但没有任何合法值时为 `null`，确实没有终态运行时为 0；合法的部分已知值可显示，但不能当作完整用量 |
| `missing_usage_runs` / `incomplete_usage_runs` | 缺少合法总 token（词元）数的运行数 / 缺少合法值或显式 `usage_complete=false` 的运行数；缺失用量使 usage 分组为 `partial` |

没有排队任务时，最老等待时间为 `null`，同时观察到队列数为 0 才能证明没有积压；不会伪造一个等待年龄。未知字段、超时、缺权限和采集失败保留 `null` / 不可用状态，不填 0。

`database.usage.cost` 与 `database.uploads.http_failure_rate` 当前均为 `null`，对应状态为 `unavailable`。没有权威账单、价格配置和 HTTP 事件分母，不能从 token 数推算实际金额，也不能把当前上传 / 文件行数变成请求失败率。这两个可选项不会单独制造严重告警。账户余额、账单、模型定价和真正 HTTP 失败率由后续独立数据来源补齐，本工具不调用提供商查询接口。

## 数据库权限与连接

维护者为监测指定独立、可从宿主机访问的 PostgreSQL 连接。角色只需连接数据库、使用 `public` schema，并读取 `jobs`、`ai_runs`、`files`、`upload_sessions`、`pdf_imports` 的聚合所需数据；生产上优先使用经过审阅的只读角色。这里不包含自动建角色、授权或提升权限的动作。

完整全局连接统计还要求 `pg_read_all_stats` 或等效现有权限。该权限可读范围较广，若未单独批准则保留缺权限状态：`connections` 为 `unavailable`，其他有权限的分组继续采集，整体不能宣称正常。不要为了获得绿色状态改用应用超级用户或自动 `GRANT`。单组 SQL 通过 savepoint（保存点）隔离，查询失败不应把其他可读分组全部变成未知。

`compose.server.yaml` 默认不映射数据库到宿主机。若已批准并启用 [`compose.backup.yaml`](../compose.backup.yaml)，可复用现场已核实的回环连接；示例端口为 `127.0.0.1:55435`。新增端口配置可能重建数据库容器，必须作为单独维护变更处理，保留卷并准备回退；不要为监测临时对公网开放数据库，也不要在运行本工具时自动应用 Compose 配置。实际连接必须对应本次要监测的数据库。

## `check`、`sample` 与 `status`

以下命令在 **Ubuntu 宿主机 `/opt/ai-notes`，已批准的运维账户 / 虚拟环境** 执行。手动命令与 systemd 应使用同一私密配置和同一数据库环境变量。环境文件由维护者在可信位置创建，内容只使用环境赋值；不要开启 shell 跟踪，也不要打印环境变量或连接值。

```bash
cd /opt/ai-notes
set -a
. /opt/ai-notes/.local/monitoring/monitoring.env
set +a
.ops-venv/bin/python -m scripts.site_monitor check --config /opt/ai-notes/.local/monitoring/config.json
.ops-venv/bin/python -m scripts.site_monitor sample --config /opt/ai-notes/.local/monitoring/config.json
.ops-venv/bin/python -m scripts.site_monitor status --config /opt/ai-notes/.local/monitoring/config.json
```

| 命令 | 行为 | 退出码 |
|---|---|---|
| `check` | 检查本地配置及私密路径；不访问数据库、Docker 或模型，不能证明采集权限和服务健康 | 0 表示配置检查完成；3 表示操作失败 |
| `sample` | 持独占锁，记录本次尝试，采集并原子更新快照及本机告警历史；标准输出只给脱敏摘要 | **0 只表示快照成功落盘，状态仍可能是 `warning`、`critical` 或 `unknown`**；3 表示操作失败 |
| `status` | 只读本地状态；读取指定数据库环境变量做目标身份比对，不建立连接、不运行采集器、不发送任何通知 | 0=`ok`；1=`warning`；2=`critical` 或 `unknown`；3=读取、配置或状态校验等操作失败 |

`status` 即使不联网，也需要获得与采集时一致的数据库环境变量；缺失、无效或目标不同不能证明旧快照属于当前目标。不要把 `sample` 的退出码或 systemd oneshot 成功当作健康探测，自动化健康判定应显式调用 `status` 并检查 JSON 的 `status` / `code`。

脱敏摘要保留 `observed_at`、`age_seconds`、当前活动告警数、严重告警数与历史事件数。完整数值、固定诊断码、当前活动事件和最多 100 条历史保存在私密 `monitor.json` 中，不发布到 Web 静态目录，不上传仓库。事件按指标键去重，级别变化记录 `updated`，只有当前可信观测证明恢复才记录 `resolved`；数据消失或从已知故障变成未知，不会关闭原有警告 / 严重事件。

## 时间、失效和容量边界

默认数据库滑动窗口为 60 分钟，过期阈值为 180 秒。快照年龄从本次采集开始时间计算，包含采集耗时。最近一次尝试未完整落盘、快照缺失、配置策略变化、目标变化、时间明显倒退或快照超龄时返回 `unknown`；旧快照不会继续显示正常。

采集按同一单调时钟预算分配剩余时间：宿主机 / Docker 最多获得 10 秒，数据库最多获得 10 秒且不超过剩余预算；剩余不足 2 秒则跳过数据库并标记超时。数据库连接、SQL 与锁等待分别设置超时。`sample_timeout_seconds` 是采集预算，**不是对整个 Python 进程的硬终止保证**：DNS / libpq 等底层操作仍需外部进程上限保护。systemd 模板用 `TimeoutStartSec=90s`、`TimeoutStopSec=5s` 和 `KillMode=control-group` 限制完整服务运行。

配置的磁盘读取和 Docker 采集共享宿主机预算；卡住的文件系统、Docker 错误、身份不符、输出超限和不完整资源数值都不能判为正常。Docker 总输出和状态 JSON 有 64 KiB 限制；活动事件最多 128 条，历史最多 100 条。超限显式失败并保留可审阅的尝试状态，不静默丢弃仍在活动的旧告警。

## 后续 Ubuntu 准备与模板启用

本节只供后续获授权的安装使用。先核对发布版本、现有运维环境、实际目标与配置，保留原有配置 / unit 文件副本，避免覆盖现场定制。安装依赖、配置数据库访问或修改系统目录均不由监测命令自动完成。

已有 `.ops-venv` 时沿用并核对依赖。没有时，在完整仓库根目录建立独立环境，使用项目锁文件，不安装到系统 Python：

```bash
cd /opt/ai-notes
python3 -m venv --copies .ops-venv
.ops-venv/bin/python -m pip install -r backend/requirements.lock
```

首次部署由维护者创建 `/opt/ai-notes/.local/monitoring` 和 `/var/lib/ai-notes/monitoring`，设置运行用户所有、`0700`。将配置示例复制为 `config.json`，按现场修改项目、服务、磁盘和阈值，设置 `0600`；已有配置应审阅差异，不直接覆盖。单独创建 `0600` 的 `monitoring.env`，仅填写 `AI_NOTES_MONITOR_DATABASE_URL`，实际 URL 和密码由安全运维流程注入，不作为命令参数或文档内容。环境文件使用真正的只读连接，不能加入真实模型 Key。

先完成 `check`、一次人工 `sample`、随后 `status`，确认未知项的原因及数据库权限；允许有明确解释的部分不可用，但不能把它登记为完整主机验证通过。手动采集只读业务数据，不需要为监测停止 API / Worker。

模板见 [`ai-notes-monitor.service`](../ops/systemd/ai-notes-monitor.service) 和 [`ai-notes-monitor.timer`](../ops/systemd/ai-notes-monitor.timer)。安装前核对 `WorkingDirectory`、`ExecStart`、`EnvironmentFile` 与 `ReadWritePaths`；状态目录必须已存在且与配置完全一致。模板只放开状态目录写权限，`UMask=0077`，清空 `DEEPSEEK_API_KEY`，没有外发命令。

以下步骤在确认手动结果后，**另行获准才执行**；现场若已有同名 unit，先保留其副本并审阅差异：

```bash
cd /opt/ai-notes
sudo install -m 644 ops/systemd/ai-notes-monitor.service ops/systemd/ai-notes-monitor.timer /etc/systemd/system/
sudo systemd-analyze verify /etc/systemd/system/ai-notes-monitor.service /etc/systemd/system/ai-notes-monitor.timer
sudo systemctl daemon-reload
sudo systemctl enable --now ai-notes-monitor.timer
systemctl list-timers ai-notes-monitor.timer
journalctl -u ai-notes-monitor.service --since today
```

timer 使用 `OnBootSec=1min`、`OnUnitInactiveSec=60s`、`AccuracySec=5s`、`Persistent=false`：系统开机后约一分钟首次运行，若启用时该时间已过，则可能立即运行；上一次服务结束约60秒后再运行，不是严格整分钟采样，也不补跑关机期间的历史采样。含义见[systemd.timer官方说明](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html)。不能把一次正常快照当作连续可用性证明。

## 更新、故障处理与回退

更新前记录当前发布版本、私密配置路径、状态目录和 unit 差异；保留 `monitor.json` 与配置的私密副本。暂停 timer，确认当前采集已结束后更新脚本 / 模板，依次执行配置检查、手动采集、状态检查及 unit 校验，再重新启用。阈值应依据实际样本调整，不能通过放宽阈值掩盖未知或权限缺失。

| 现象 / 代码 | 处理方向 |
|---|---|
| `monitoring_config_unavailable` / `monitoring_state_unavailable` | 核对运行用户、目录所有者、文件权限和存储空间；不输出私密内容 |
| `monitoring_database_environment_missing` | 核对当前 shell / service 是否加载正确环境文件；不把密码写到命令参数 |
| `database_stats_permission_denied` | 保留全局连接统计不可用；需要时单独评估统计角色权限，不自动提权 |
| `monitoring_snapshot_stale` / `monitoring_sample_incomplete` | 查看 timer、service 和存储错误；保留旧状态供审阅，重新完整采集后确认 |
| `monitoring_target_changed` | 确认目标修改是否有意；新目标配置新的 `state_root`，不修改旧指纹绕过保护 |
| `monitoring_policy_changed` | 核对新窗口 / 阈值，完整采集后再判断，不手改旧 evaluation |
| `monitoring_locked` | 核对是否有另一采集进程；锁文件可长期存在，不能仅凭存在就删除 |
| Docker / 宿主机不可用 | 核对实际平台、宿主机运行位置、精确项目 / 服务身份与本机 socket 权限 |

停用与回退仅影响监测服务，不操作业务容器或数据库：

```bash
sudo systemctl disable --now ai-notes-monitor.timer
sudo systemctl stop ai-notes-monitor.service
systemctl is-active ai-notes-monitor.service
```

停止中的采集可能留下 `running` 尝试，后续状态为未知，这是保留现场的预期行为。保留私密配置与状态，恢复此前脚本 / unit 副本并运行 `daemon-reload`、`check`、人工采集后再决定启用；不为回退删除状态、数据库卷或对象，也不执行数据库 downgrade。目标改变时另建状态目录。

## 本机告警与后续验收

本工具只有本机事件和脱敏 journal 摘要，**没有邮件、Webhook 或其他外部通知渠道**。本机写入成功不等于通知送达；主机断电、网络失联、定时器未运行或磁盘不可写时，需要主机外独立监测。外发渠道与失联检测仍是后续运维工作，不由本次模板自动完成。

请用 [M1 实机与性能验收记录](M1实机与性能验收记录.md) 记录真实 Ubuntu 指标、权限不足与超时、阈值告警、去重 / 恢复、超龄和外部失联覆盖情况。真实设备、代表性数据、真实模型、账单、HTTPS、云端恢复与公网发布均须分别验收；当前工具落盘不能替代这些结论。
