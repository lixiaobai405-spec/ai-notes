# 定时备份与失败通知

本轮交付独立宿主机执行器、保留策略、可选通知接口和 systemd 模板；**尚未安装或启用公网定时任务，尚未发送真实外部通知**。当前开发库与公网保持原状。设计见 [已确认方案](superpowers/specs/2026-10-25-scheduled-backups-design.md)。

## 运行方式与数据范围

`scripts/site_backup_schedule.py` 使用标准库，调用现有 [整站备份工具](整站备份与隔离恢复.md)，覆盖 PostgreSQL 和数据库引用的 OSS 原件、PDF、变体及 AI 历史来源。执行工具仍需要完整仓库、后端依赖与宿主机 Docker CLI；它不在 API/Worker 内运行，不给应用容器挂载 Docker socket。

默认北京时间每天 03:00 开始，只允许 UTC 19:00 起 60 分钟内启动；配置与 timer 必须一起修改。timer 不补跑错过的日期，runner 拒绝窗口外运行，避免白天突然停服。窗口限制的是开始时间，不承诺在窗口结束前完成；备份子进程默认最多 30 分钟，systemd 限制整体服务 55 分钟。

执行顺序是：校验配置及独占锁 → 记录原运行容器 → 停止 API/Worker → 确认写入者停止 → 备份与校验 → 恢复原服务并等待 API healthy → 登记回执 → 清理旧备份。只恢复原本运行、容器 ID/项目/服务身份仍一致的服务，不拉镜像或执行迁移；原先停止的 Worker 不自动启动。

启用者必须保证没有其他数据库/OSS 写入者，包括迁移、其他 Worker、副本、上传脚本及对象生命周期删除。`writers_exclusive_confirmed` 默认 false，只有完成检查后才改为 true。项目部署、手工维护与本执行器必须串行，不能在备份期间更换容器。

## 启用前准备（Ubuntu 宿主机，未在本轮执行）

1. 检查 Git 工作区、实际 Compose 项目名/覆盖文件、镜像提交和现有端口修改；不要覆盖服务器已有配置。保留当前手工备份和恢复路径。
2. 在完整仓库旁建立独立运维环境。路径不能是软链接；普通 Linux venv 的 Python 通常是链接，因此使用 `--copies`：

```bash
cd /opt/ai-notes
python3 -m venv --copies .ops-venv
.ops-venv/bin/python -m pip install -r backend/requirements.lock
```

3. 现有 `compose.server.yaml` 不映射数据库。现有整站工具严格要求本机回环数据库连接，另提供 `compose.backup.yaml`，只绑定 **127.0.0.1:55435**，不对公网开放。把它加入服务器原有 Compose 文件集合；首次应用端口配置可能重建 DB 容器，必须在另行批准的维护窗口停止写入服务、保留卷并检查恢复。后续所有 Compose 命令使用同一集合，不使用 `down -v`。这一步不是调度器自动执行的动作。
4. 用私密配置文件生成连接文件，不在命令行或日志写入密码。以下代码只写本机文件；已存在的文件会拒绝覆盖：

```bash
umask 077
mkdir -p .local .backups/scheduled .local/backup-schedule-state
chmod 700 .local .backups/scheduled .local/backup-schedule-state
.ops-venv/bin/python - <<'PY'
import os
from dotenv import dotenv_values
from sqlalchemy.engine import URL
values = dotenv_values('.env.server', interpolate=False)
url = URL.create('postgresql+psycopg', username=values['POSTGRES_USER'],
                 password=values['POSTGRES_PASSWORD'], host='127.0.0.1',
                 port=55435, database=values['POSTGRES_DB'])
descriptor = os.open('.local/backup-database-url.txt', os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
with os.fdopen(descriptor, 'w', encoding='utf-8') as target:
    target.write(url.render_as_string(hide_password=False) + '\n')
PY
cp -n ops/backup-schedule.example.json .local/backup-schedule.json
chmod 600 .local/backup-schedule.json
```

连接文件、`.env.server` 与实际 db 容器必须指向同一集群；原工具会比较数据库名、PostgreSQL 主版本和集群标识，不放宽这个保护。配置中的所有路径使用实际绝对路径，`compose_files` 包含服务器正在使用的完整文件集合；避免软链接、junction 和路径重叠。

5. 完成外部写入者检查后才设置 `writers_exclusive_confirmed=true`。若使用本地对象目录，把 `storage_backend` 改为 `local`、设置 `storage_root`，并将 `oss_env_file` 改为 null；备份根、状态根与源文件目录不能相互包含。

## 手动检查、首次执行与安装

在 `/opt/ai-notes` 执行。`check` 只检查路径/配置，不调用 Docker 或访问数据库/OSS；它不能代替实际连接检查。`run` 会产生维护窗口并下载备份对象，应在批准窗口首次运行：

```bash
.ops-venv/bin/python scripts/site_backup_schedule.py check --config .local/backup-schedule.json
.ops-venv/bin/python scripts/site_backup_schedule.py run --config .local/backup-schedule.json
.ops-venv/bin/python scripts/site_backup_schedule.py status --config .local/backup-schedule.json
.ops-venv/bin/python scripts/site_backup_schedule.py retention-plan --config .local/backup-schedule.json
```

状态 `backup_verified=true` 仅说明备份内容校验，`services_restored=true` 说明原服务已恢复；`ok=true` 要求整个流程完成。文件哈希正确不代表已实际恢复演练或具备异地灾备。

确认手动执行与恢复演练满足需求后，再另行安装模板：

```bash
sudo install -m 644 ops/systemd/ai-notes-backup.service ops/systemd/ai-notes-backup.timer /etc/systemd/system/
sudo systemd-analyze verify /etc/systemd/system/ai-notes-backup.service /etc/systemd/system/ai-notes-backup.timer
sudo systemctl daemon-reload
sudo systemctl enable --now ai-notes-backup.timer
systemctl list-timers ai-notes-backup.timer
journalctl -u ai-notes-backup.service --since today
```

模板使用 [Type=oneshot 与 TimeoutStartSec](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html)，而非不适用于 oneshot 的 RuntimeMaxSec；[timer](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html) 设置 `Persistent=false`。模板的 ReadWritePaths 必须与实际配置一致。

## 保留策略

默认保留最近 **7 份当前可完整验证**的成功备份，可配置 1–365。只删除调度器专用根内、带有独立私密成功回执的旧目录；目录名为 `scheduled-UTC时间-随机标识`。手工备份、未知目录、暂存、损坏、回执不匹配及旧 schema 无法由当前版本验证的备份均保留并报告。

只有本次新备份验证通过且原服务恢复成功才会清理。失败时不先删除旧副本腾空间。`retention-plan` 是依据回执的只读初步候选，实际清理还要完整验证，结果可能更保守。状态与计划只显示各类总数和前 20 项样本，避免大量历史目录使状态超限；未知目录名以固定占位保护隐私。清理逐项检查固定文件集合，遇到新增文件或身份变化即停止；发生磁盘 I/O 故障时旧候选可能只删除一部分，应检查 skipped 记录，不能当成完整可恢复备份。

当前旧 schema 备份可能持续占用空间，应保留对应代码和运维环境进行人工验证处理；不为清理而放宽恢复 schema 检查。此策略不删除 OSS 原件、历史版本或回收站，也不等于统一引用 GC。日/周分层、ECS 外独立副本与失联监控仍为后续工作。

## 失败记录与可选通知

状态根包含 `status.json`、`recovery.json`、`receipts/`、`events/` 和稳定 OS 锁文件。Linux 目录/文件限制为 0700/0600。实际命令执行限定于 POSIX，生产调度目标为 Ubuntu；Windows 在创建子进程前返回 `schedule_platform_unsupported`。Windows 单元测试验证替身调度、路径、原子性及锁，实际进程终止专项在隔离 Linux 容器中运行；Windows chmod 不替代 ACL 权限管理。

失败事件先落盘，包含 event_id、run_id、UTC 时间、阶段和固定错误码，不包含笔记、数据库 URL、OSS 对象键、原始异常或子进程输出。默认 `notification_command=[]`，**只提供本地事件和 journal 告警记录，不宣称已主动推送**。

如需外部通知，管理员另行提供可信绝对路径程序并配置 `notification_command`；程序从 stdin 接收脱敏 JSON，不接收 shell 拼接文本。渠道凭据在程序自己的私密配置中管理，不能作为命令参数或回显。执行器默认最多等待 15 秒，通知失败不会掩盖原备份故障。

```bash
.ops-venv/bin/python scripts/site_backup_schedule.py retry-notifications --config .local/backup-schedule.json
```

重试使用同一 event_id，接收端应按该 ID 去重。外部发送成功与本地确认之间崩溃可能重发，不能承诺恰好一次；delivered 仅表示通知程序退出 0，最终送达语义由该程序负责。未配置渠道、数据库故障和整个应用停止都不会阻止本地记录，但宿主机断电、磁盘满、定时器未启用等仍需独立外部监控。

## 故障恢复与停用

备份失败会尝试恢复原服务；若恢复失败，保留 `recovery.json`，新备份拒绝覆盖现场。systemd 的 ExecStopPost 在异常退出后再次执行幂等恢复。也可人工运行：

```bash
.ops-venv/bin/python scripts/site_backup_schedule.py recover-services --config .local/backup-schedule.json
```

容器 ID 变化时拒绝操作新的容器，应按原项目部署记录人工核查；不要删除 recovery 文件绕过检查。操作系统强杀/断电可能留下未登记备份或隐藏暂存，不会自动删除。Docker 客户端退出不保证容器内 pg_dump 立刻退出，排查时核对容器进程与数据库；备份只读操作不等于恢复操作。

暂停未来任务可 `sudo systemctl disable --now ai-notes-backup.timer`，这不停止正在运行的备份。需要中断当前运行时先记录状态，再 `sudo systemctl stop ai-notes-backup.service` 并运行恢复命令，检查原服务健康。保留备份、状态及私密配置，不删除数据库卷、不执行 downgrade。修改调度或移除模板前先确认没有活动任务。
